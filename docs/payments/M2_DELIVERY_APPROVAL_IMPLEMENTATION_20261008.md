# TheFEYA — M2 exact delivery approval

Continuation of MASTER commerce execution v1.2, the owner's manual shipping/profile instructions and PR #71. This package closes the gap between saving a private draft and recording the owner's review of a particular version. It does not yet connect approved delivery estimates to the public bag or payable checkout.

## Behavior

The existing `/admin/company/delivery` adds a check of the saved version and a separate **Утвердить сохранённую версию** action. Changing a draft requires saving and checking the new version before approval.

The check covers every configuration with a current offer, resolving configuration → product → default assignments independently for shipping and production. It checks offer currency, served countries, baseline coverage, rule ambiguity, enabled-method amounts, production/transit day basis, calendars, scheduling time zone/cutoff, parcel combination and quantity rules. Explicit disabled methods remain disabled. Postal restrictions never acquire a fallback just to pass approval. A served country must have at least one baseline method; intentionally unsupported country areas may be excluded by postal rules.

Unassigned examples and experimental profiles remain outside the approved operational scope. The $19/$35 draft is not converted to EUR, automatically assigned or approved. A used USD profile against an EUR offer blocks approval. Configurations without a current offer stay outside this approval scope; future quotes must revalidate their actual current offers.

Mechanical completeness does not confirm business facts, carrier SLAs, tax treatment, capacity allocation or legal transaction roles. The button records the verified owner's separate business review. For custom specifications, the future quote must still wait for the agreed specifications/production start; approval is not an individual order's production booking.

## Authority and safety

- New private contract: `commerce_delivery_approval_v1`; validation: `commerce_delivery_approval_readiness_v1`.
- Migration: `20261008083213_commerce_delivery_approval_v1.sql`, generated by Supabase CLI 2.117.0.
- Immutable approvals reference exact saved workspace ID/revision/hash, a server-computed catalog hash, trusted actor, request ID and fixed business-review contract.
- One separate approved pointer, initially absent. Draft edits do not change that pointer or rewrite historical approvals.
- Compare-and-swap checks both draft and approved revisions; the advisory transaction lock is shared with draft saves. Catalog changes reject the candidate.
- Same-request retries first look up the exact existing result. A lookup-only call cannot approve anything; an old successful retry does not rewind a head, even after a later draft/approval.
- RLS and explicit grants deny anon/authenticated access. Service role has SELECT and bounded RPC execution, without direct table DML. SECURITY DEFINER has empty search paths; actor authorization happens in the protected server before the service-only RPC. No browser request may supply actor, readiness validation, approval clock or public/payment capabilities.
- The protected server derives detailed completeness from one database context; the database binds the current draft/catalog and verifies the report contract and counts. A service credential is privileged and must never reach the browser.
- New server-only `FEYA_DELIVERY_WORKSPACE_APPROVAL_ENABLED=false`, independent of draft editing. Existing general owner actions, rates, payments and analytics stay under their own gates. Every approval response explicitly keeps public rates, payment and provider sessions false.
- With approval disabled, draft reads/saves/previews continue using the prior storage RPCs; deploying the code alone does not require the new approval RPC to be called or enable approval.

No rates, examples or approvals are seeded. No public visual, SEO, Product Truth, offer amount or published policy is edited.
