# Operating the guest withdrawal service

The buyer opens the public returns page, reviews the declaration and confirms it. The site records the name, contract identifier or description, chosen acknowledgement email, declaration, database timestamp and receipt reference together. The studio case, acknowledgement job and, when configured, a separate full declaration for the legal seller are committed before the public API returns a receipt. Payment records and refund decisions follow their existing processes.

The intended legal benchmark is a timely acknowledgement on a durable medium giving the statement's contents and its submission date and time. A website receipt, a downloaded copy and the private delivery status do not prove arrival in the buyer's mailbox. [Directive (EU) 2023/2673, Article 11a](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32023L2673)

## Installation and activation

1. Under the studio's existing `manager.feya@gmail.com` account, prepare a private standalone Apps Script with `scripts/withdrawal-gmail/Code.gs` and `appsscript.json`. The mailbox owner runs `authorizeStudioMail` and grants the listed permissions. This verifies the studio identity and prints only the public OAuth audience. Pairing may be completed while the website is still in draft. It uses no mailbox, timer or website endpoint.
2. The operator deploys the reviewed routes and migration with `FEYA_WITHDRAWAL_LIVE=false` and sets `FEYA_WITHDRAWAL_GOOGLE_AUDIENCE` to the public audience above. After the canonical endpoint is ready and paired, run `installWithdrawalWorker` in the same authorized private project under the studio account. This installs a single five-minute timer using the existing grant. Database credentials stay on the server. [Apps Script identity](https://developers.google.com/apps-script/reference/script/script-app#getidentitytoken), [MailApp](https://developers.google.com/apps-script/reference/mail/mail-app), [installable triggers](https://developers.google.com/apps-script/guides/triggers/installable)
3. Before opening intake, verify two successive timer polls against the paired endpoint using the restricted `select public.feya_withdrawal_health_v1()`. It reports the actual poll time, Google quota and the oldest outstanding acknowledgement. In an isolated staging environment, use the identical migration, two controlled mailboxes, an authorized worker pinned to the staging origin and a clearly labelled synthetic notice. Verify the message by opening the independent recipient inbox and checking the declaration, entered name, contract details, chosen address, UTC time and receipt reference. Also verify a lost number and an alternative address, recipient verification, a mail outage, a missed report and the studio's private case handling. Keep test statements out of the production contract register.
4. Set `FEYA_WITHDRAWAL_SELLER_ROUTE` only for the actual arrangement. Use `seller_mailbox` when Seller-Online LLC accepts its published `office@seller-online.com` for declarations and recognises the original submission time. This route automatically queues the complete statement for that fixed address. Use `studio_mandate` only when a then-effective written appointment authorises TheFEYA to receive declarations for the seller at filing. That mode does not send a second copy to the legal seller automatically. In both modes the studio's ordinary Gmail alert contains only the reference and time. Staff review the restricted queue and follow up in the event of an interruption. Without a selected route the public form stays off. The direct seller email is available on the returns page.
5. The responsible studio operator must have restricted access to the queue, be assigned to respond promptly, and know how to check bounced or undelivered Gmail notices, handle a recipient who wrote from another mailbox, and make customer contact through the existing support channel. Agree the retention criteria and deletion procedure for real notices. This migration has no automatic deletion of completed notices. Record the controlled inbox evidence and who monitors the queue, then enable the feature and check its public and guest entry points with the first genuine case.
6. To pause admission, set `FEYA_WITHDRAWAL_LIVE=false`. Continue to run the worker and clear already accepted cases. Before rotating the script project, pin its new public audience explicitly. Removing the timer or audience stops delivery and requires active handling of all outstanding cases.

## Controlled delivery rehearsal

Use a separate staging site and database, a private copy of the worker, and two real mailboxes controlled by the studio. Do not send a fictional withdrawal to the seller or a customer. A test delivered only to the sending Gmail inbox is a self-send test. Choose an independently controlled receiving inbox for the full handoff check. The rehearsal needs no paid sender or new email provider.

1. Pin the staging HTTPS worker endpoint in both the private rehearsal copy of `Code.gs` and its manifest's `urlFetchWhitelist`. Pin that script's audience only on staging. Do not broaden the allowlist or point rehearsal data or credentials at production.
2. Load a synthetic checkout on staging and use an explicit identifier such as “STAGING MAIL TEST — no customer contract”. Only the test database uses a paid-status fixture for checkout identity matching. The selected recipient is the controlled test inbox. A second case with a free-text purchase description exercises the manual verification route.
3. Run `authorizeStudioMail` separately. It prints the public audience and creates no trigger. Run `runWithdrawalWorker` manually on the isolated environment to exercise dispatch without a scheduler. Open the independent inbox and compare the actual content, language, receipt reference, entered contact details and UTC timestamp with the stored synthetic case. Google handoff, sent-folder entries and the web receipt alone are insufficient evidence of inbox delivery.
4. Exercise the seller-receipt states using simulation evidence. To test `seller_mailbox` dispatch, use a staging-only mail sink or a rehearsal script that redirects mail addressed to the fixed seller recipient to a second studio-controlled inbox. Block every other external recipient in this rehearsal. Verify the complete statement at the sink and exercise a successful send without confirmed receipt as separate states. Never label this rehearsal as evidence that Seller-Online accepted a real notice or authorised the studio. Capture test outcome, time and reference without personal details. Use `installWithdrawalWorker` separately only when the intended permanent endpoint and account are paired and ready.

## Delivery and capacity

MailApp exposes a remaining daily recipient allowance and returns no message ID from `sendEmail`. `submitted` means the call returned without an exception or the studio later confirmed submission. Only an observed inbox receipt proves the specific test delivery. The script stores only the job ID, attempt ID and outcome when a report must be retried. The database grants the message content to one dispatch attempt. An inconclusive result enters private review. The stable receipt reference also appears in the message subject. [MailApp method reference](https://developers.google.com/apps-script/reference/mail/mail-app)

Consumer Apps Script currently allows 100 recipients per day across the account's use. Each run checks Google's actual remaining quota. This application caps its own grants at 90 per rolling 24 hours, prioritises customer receipts, then seller declarations, then studio alerts, and caps studio email alerts at ten in that window. The last twenty available Google recipients, and the final twenty grants in this service’s own allowance, are reserved for customer acknowledgements. Monitor the seller-dispatch backlog and follow up promptly through the agreed channel when quota prevents automatic handoff. All cases remain in the studio queue even after the email alert limit. Quota exhaustion, delayed triggers or sustained traffic can delay durable acknowledgements. The operator must monitor case ages and unresolved receipts independently of email alerts. [Google quotas](https://developers.google.com/apps-script/guides/services/quotas)

## Private case handling

Use the restricted Supabase SQL console, or a server-side operator with the equivalent access. Browser roles have no table or RPC privileges. The Google worker can take one ready message or report one attempt. In seller-mailbox mode the full statement is addressed only to the fixed seller destination. It cannot look up orders, read the case register, send arbitrary messages or decide a refund.

- List outstanding cases with `select * from public.feya_withdrawal_open_cases_v1(100)`. The list contains references, timestamps, recipient-verification need and job states. Use `feya_withdrawal_case_v1(reference)` only on the individual case under review.
- A paid customer's order number, checkout name and original mailbox can authorize a confirmation for that mailbox. The customer may supply an alternative contract description or email. The notice is accepted immediately and the studio must verify control of the submitted mailbox and the case promptly before sending the statement there. Record the restricted evidence reference with `feya_withdrawal_verify_recipient_v1(reference, verified_email, actor, evidence_reference)`. A failed match cannot replace the declaration's original address. No email token is required to file. An optional checkout token never authorizes an unrelated recipient.
- When a send/report is interrupted, the taken job cannot automatically be sent again. After 15 minutes the next worker poll flags it for review. Check the precise attempt ID and receipt with the sender and recipient through an established channel. If independent evidence confirms a handoff, record `feya_withdrawal_reconcile_job_v1(job, attempt, 'confirmed_submitted', actor, evidence_reference)`. Release the same message for another attempt only with positive evidence the earlier one was not sent. The function requires the exact attempt and imposes at least one hour before a `confirmed_not_sent` replay. An empty Sent search or absent read receipt is insufficient.
- A private alert to the studio, a customer acknowledgement and receipt by the legal seller are separate events. Use `feya_withdrawal_case_v1(reference)` to read the original declaration, name, chosen contact, contract details and original UTC time. In seller-mailbox mode the queued message contains these details and the original submission time. In delegated mode use the seller's agreed channel when its operating procedure calls for a handoff. Do not forward an unrestricted database view, bearer link, checkout token or identity documents.
- If a written mandate already made the studio the seller's recipient when the buyer filed, record its restricted evidence reference with `feya_withdrawal_confirm_seller_receipt_v1(reference,'authorised_studio',null,actor,evidence_reference)`. That records the filing time as receipt. For an actual acknowledgement from Seller-Online, supply `'seller_confirmed'` and the seller's evidenced receipt timestamp. The private audit records the operator and recording time independently. Neither a sent email, the studio alert nor an unconfirmed promise is seller acknowledgement. Follow `awaiting_seller` and `oldest_awaiting_seller_utc` in the health report and chase outstanding receipts.
- For a bounce after a reported handoff, use the case reference, contact the verified customer promptly via the established channel and document the resolution with support. The worker does not read Gmail. Monitor both the mailbox and cases until handled. Mark the studio action complete using `feya_withdrawal_resolve_case_v1(reference, actor)` after recording seller receipt and handling the case. An unresolved seller handoff prevents closing the case. The filing time remains unchanged.

The raw IP and optional checkout token are absent from the case data. The service keeps bounded hourly counts using hashes for IP and mailbox quotas; inactive buckets age out on new intake after 48 hours. Keep personal data and Google identity tokens out of URLs, monitoring payloads, case exports and support diagnostics.
